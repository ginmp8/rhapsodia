# Analysis Contract

## At a Glance
- **Purpose:** Specify concise human-facing answers and an optional machine-checkable flow-analysis artifact.
- **Load when:** Producing reviewable, reusable or programmatically validated flow models rather than answering a simple code-location question.
- **Decision impact:** Sets minimum evidence fields, status enums, references, negative-claim controls and what the bundled validator can prove.

## Human report: smallest sufficient format

**Answer and boundary:** direct answer, material assumptions, revision/environment and what was actually inspected.

**Mechanism:** ordered entry -> guard -> transition -> effect -> exit. A short causal narrative plus one diagram or table only where useful. Include async handoffs and other writers if they can change the answer.

**Evidence ledger:** ID, claim, class, condition, source locator; source IDs should be resolvable to concrete file/symbol/line, configuration entry, test execution, or trace.

**Challenge result:** one or more counterpaths or failed attempts with exact status, followed by unknowns and the smallest next check. An unsupported proof obligation is a gap, not a positive result.

**Verdict:** `supported-within-scope | contradicted | insufficient-evidence`. No universal truth claim unless the closed-world proof requirements are met.

## Optional typed JSON artifact

Use `assets/analysis.schema.json` as the model contract and `scripts/validate_analysis.py <path>` for deterministic validation. Keep analysis artifacts *outside* the skill package or frozen source tree unless the user requested otherwise. Fields:

- `schema_version`: `1.0`.
- `question`, `mode`: one question and `understand|challenge|change-impact`.
- `scope`: `{repository, revision, inspected_paths, closed_world, limitations}`; `closed_world` requires explicit reasoning beyond a flag.
- `sources[]`: stable `id`, `kind` (`code|config|test-definition|test-run|trace|log|document|user-report`), `locator`, `revision_or_context`.
- `claims[]`: stable `id`, `statement`, `status`, `source_ids`, `conditions`, `universality` (`local|bounded|unproven`), `countercheck`.
- `transitions[]`: `id, from, to, trigger, guard, claim_ids`; preserve guarded edges even when a diagram omits detail.
- `checks[]`: `id, question, method, status` (`passed|failed|not-run`), `source_ids`; executed checks should cite test-run or trace evidence.
- `gaps[]`: `id, question, why, next_check`.
- `verdict`: `supported-within-scope|contradicted|insufficient-evidence`.

Hard mechanical gates: a claim with `static-observed` needs a code/config/test-definition source; `runtime-observed` needs test-run/trace/log evidence; all IDs must resolve; `bounded` claims require `scope.closed_world=true` and at least one passed check. The validator **cannot prove** closed-world completeness, correct interpretation, test coverage or source authenticity; those require code/trace investigation and independent review when material.

See `examples/sample-analysis.json` for an illustrative synthetic artifact and `examples/sample-report.md` for presentation. Neither is real execution evidence. When writing JSON through an LLM, validate generated bytes instead of declaring compliance from memory.
