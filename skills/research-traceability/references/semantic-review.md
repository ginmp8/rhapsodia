# Semantic Trace Review

## Purpose

Validate the truth of trace links independently from structural coverage.

Use fresh context or an independent reviewer when available. Do not let the authoring pass approve its own subjective interpretations without an explicit review step when the changes are material.

## Review dimensions

### 1. Source -> finding fidelity

For each finding:
- verify the cited source actually supports the claim;
- preserve scope, version, jurisdiction, qualifiers, and uncertainty;
- reject stronger wording than the evidence supports;
- detect cherry-picking when credible contradictory evidence exists.

### 2. Finding atomicity and deduplication

Check whether each finding is one independently actionable claim. Split compounds. Merge true semantic duplicates while preserving all supporting source IDs.

### 3. Finding -> requirement derivation

Verify that the requirement follows from the accepted finding and does not introduce an unrelated architectural preference.

Ask:
- Is this operational behavior actually implied by the evidence?
- Is the requirement narrower than necessary or broader than justified?
- Were important qualifiers lost?

### 4. Requirement -> change satisfaction

Inspect the exact target location, not only the change summary. Verify the implementation satisfies the requirement in actual behavior and does not silently weaken another requirement.

A structurally linked change that does not satisfy its requirement is a failed trace.

### 5. Requirement -> evaluation adequacy

Verify the evaluation can falsify the requirement when the behavior is wrong. Reject tautological checks that only inspect the same text generated by the candidate.

Use objective validators for objective properties and review/scenario evidence for semantic behavior.

### 6. Reverse justification / gold-plating check

Inspect every substantive candidate change. If no requirement requires it:
- remove it; or
- add a legitimate requirement only if an existing finding supports it.

Never invent a finding retroactively to justify a preferred change.

### 7. Exclusion accounting

Review every `rejected`, `not-applicable`, `uncertain`, and `conflict` disposition. Confirm the rationale is evidence-based and not merely a mechanism for avoiding implementation work.

### 8. Completeness boundary

Verify final language claims only corpus-bounded completeness. A trace matrix cannot prove the research found everything that exists.

## Review result

Use one of:
- `pass`: no material semantic trace defect;
- `pass-with-limitations`: trace is sound but evidence/runtime gaps remain explicit;
- `fail`: one or more material links are invalid or unsupported.

Record concrete failed IDs and the causal issue. Avoid generic quality scores when a specific relation can be identified.
